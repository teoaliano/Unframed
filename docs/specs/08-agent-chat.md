# 08 · Agent chat

Depends on: 01, 02, 03, 04, 05, 06, 07

## Problem Statement

Spec 07 gives the engine chats that run on Claude or Codex, read and change the canvas, ask for permission and survive restarts. None of that is usable until a person can see it: start a chat about what they selected, watch the agent work, answer its approvals and questions, read its replies, see what each turn touched and take a turn back.

The old app had a chat rail with tabs filtered by the selection, a composer with model, reasoning and mode pickers, and a recap of the artifacts a chat touched. The rewrite keeps all of it and replaces the composer, the transcript, the work log, the approval panel and the plan flow with t3code's versions, because t3code's are better and its engine is what spec 07 rebuilt. It also adds t3code's thread search and its per-turn diffs (for page and motion files). t3code's preview tools, which let the agent look at what it made, need spec 09's preview origin and are built there.

## Solution

A rail on the left of the canvas, where the artifact editor's chat column sits, holds the project's chats as tabs, filtered by the selected artifacts. Under the tabs, a t3code transcript: markdown replies, streamed as they arrive, tool calls folded into work groups, sub-agent rows, the pending approval and question panels, proposed plan cards, and a recap card per turn listing what it touched with Editor, Locate and Revert this turn. Below it, the shared composer of spec 03 in its Agent tray, built 1:1 on t3code's composer: a Tiptap editor, the selection as context chips, attachments, slash commands, the model, traits and runtime mode pickers, the plan toggle, the context window meter, queued messages, the prompt stash, ArrowUp history and Edit from here.

The selection toolbar's Agent button opens the same composer on the selection and says whether the message continues an earlier chat or starts a new one. The editor of spec 09 embeds the same rail as its left column.

The engine side of this spec is small: thread search and per-turn diffs of page and motion files.

## User Stories

The rail

1. As a person, I want an Agent button in the bottom bar that opens a chat rail on the left, so that the conversation sits beside the canvas instead of over it.
2. As a person, I want the rail to slide in and out, and only fade when I have asked for reduced motion, so that it reads as one surface arriving and leaving without making anyone queasy.
3. As a person, I want the rail to sit under the top bar while it is open, so that the logo and the tabs stay in reach and one corner never holds two sets of controls. Settings is in the top bar's far end (spec 17), so it stays in reach too.
4. As a person, I want closing the rail mid-turn to change nothing, so that the turn finishes and is there when I reopen it.
5. As a person, I want to start a new chat, delete the current one after a confirmation, and close the rail from its header, so that the rail's own controls are always in one place.
6. As a person, I want deleting a chat to leave its canvas changes in place, so that removing a conversation never removes work.
7. As a person using the artifact editor, I want the same rail embedded as the editor's left column, without a close button or Locate, so that one chat UI serves both places.

Tabs and search

8. As a person, I want one tab per chat, as many inline as the rail's width holds and the rest under More with their count, so that a narrow rail never pushes its tabs past its edge.
9. As a person, I want a spinner on a chat whose turn is running and a checkmark on one that finished since I last viewed it, so that I can see which chats are busy and which have news.
10. As a person, I want to double-click a tab to rename it, Enter or clicking away to commit and Escape to abandon, so that renaming is quick and safe to start by accident.
11. As a person, I want a tab to read my name, else the agent's name, else the opening words, else "Chat", so that every tab says something.
12. As a person, I want the tabs filtered to the chats tagged with any selected artifact, and all chats when none is selected, so that selecting an artifact shows what was said about it.
13. As a person, I want the active tab always to be one I can see, so that the composer always sends to what is highlighted.
14. As a person, I want to search chats by what was said in them, so that I can find an old conversation without scrolling tabs.

No provider

15. As a person with no provider ready, I want the rail to show each provider's status, how to install it and a Check again button, so that I know what to do and nothing is sent anywhere until then.

## Implementation Decisions

### Modules

### The rail

- The bottom bar's **Agent** button (spec 02; sparkles icon, pressed while the rail is open) opens and closes the rail. The rail is 380 px wide, docked to the left edge from the top bar's bottom border (36 px, spec 17) to the window's bottom, over the canvas, where the artifact editor's chat column sits, on solid `--background` (spec 12: on glass it crossed spec 02's pan budget) with the kit's right border and square corners. The Agent header is its first row. While it is open (and the artifact editor is not, spec 09) the top bar runs square from the window's left edge, with no end curve there, so its bottom border and the rail's right border meet with no gap; the top-left chrome card (`.unframed-chrome-left`, spec 02) keeps its place in the bar and drops its glass, border and shadow. The bottom row of the canvas (the zoom controls and the bottom toolbar) starts beside the rail, and the toolbar centres in the canvas the rail leaves. Bottom-left toasts start beside the rail too, so none covers its composer. The diff panel opens beside the rail, on its canvas side.
- **Narrow windows.** Below 1280 px wide the rail does not dock, because a full-height rail leaves too little canvas for the zoom controls, the bottom toolbar and the tldraw watermark side by side: it opens as the kit Sheet from the left, `min(88vw, 24rem)` wide, over the Sheet's backdrop, with the same header, tabs, transcript and tray. The top-left card stays as it is. Close, Escape (when no menu of the rail's own takes it) and a click on the backdrop close it; Locate and Editor close it before they act on the canvas.
- **Motion.** Opening slides the rail in from `translateX(-100%)` with `opacity 0` to rest: `transform 260ms` on t3code's `--ease-drawer` curve (`cubic-bezier(0.32, 0.72, 0, 1)`) and `opacity 200ms ease-out`. Closing reverses it faster: `transform 200ms` on the same curve and `opacity 160ms ease-out`. It is a CSS transition, not keyframes, so reopening mid-exit reverses from where it is; the enter uses `@starting-style`. Under `prefers-reduced-motion: reduce` there is no transform, only `opacity 160ms ease-out`. The rail stays mounted through its exit and unmounts on its own `transitionend` (transform or opacity, on the rail element itself), with a 600 ms timer as the guarantee, since a hidden tab fires no transition events.
- **Embedded mode.** The editor (spec 09) mounts the same rail as its left column: no transition, no Close, no Locate, and its tab strip filtered to the artifact being edited.
- **Header**: a sparkles icon and the heading "Agent", then the kit's ghost icon Buttons, Search chats (below) and three more: **New chat** (tooltip "New chat about the selected artifacts" when artifacts are selected, else "New chat"; disabled with no provider ready), **Delete chat** (tooltip "Delete this chat"; disabled with no chat or while it runs), **Clear all chats** (brush icon, tooltip "Clear all chats"; not in embedded mode, where the strip shows one artifact's chats), then a short vertical kit Separator and **Close** (not in embedded mode). Clear all chats is unavailable when every chat of the project is running or there is none; it is then marked `aria-disabled` rather than `disabled`, so its tooltip still says why: "Every chat is still running" or "No chats to delete". The separator keeps Close apart from Clear all chats, so a reach for Close never lands on the bulk delete; Clear all stays a one-click header button like the others, with its confirmation as the guard, because a menu holding one action would hide it for nothing.
- **Delete** asks first, in the kit's alert dialog (spec 12): title "Delete this chat?", description "The conversation is removed for good. What the agent changed on the canvas stays.", action "Delete chat" (the destructive Button). It dispatches `thread.delete`; canvas changes and files stay.
- **Clear all chats** deletes every chat of the project, not only the tabs the selection filter shows, except the running ones, which finish their turns and stay. It asks first, in the same alert dialog: title "Clear all chats?", description "This deletes <n> chat(s) for good." then, when some are running, "1 running chat is kept and finishes its turn." or "<m> running chats are kept and finish their turns.", then "What the agent changed on the canvas stays.", and the action "Delete <n> chat(s)" (the destructive Button). The counts are taken when the dialog opens. It dispatches spec 07's `project.chats.clear`, and the engine picks the chats that are not running when the command runs, so a chat whose turn started in between is kept. There is no undo. Once the shell has caught up with the command, a toast (the app's info toast) says what happened, counted from the chats that actually left: "Deleted <n> chat(s)", and when running chats stayed, "1 running chat was kept." or "<m> running chats were kept." on its second line.
- Closing the rail mid-turn changes nothing on the engine; reopening shows the turn where it is.
- **Copying.** Copy and Cut inside the rail (the keyboard shortcut or the browser menu) act on the text the person selected in the rail, as plain text, even while shapes are selected on the canvas. The rail stops tldraw's document-level copy and cut from taking the canvas selection. The composer's own copy and the code blocks' Copy button are unchanged.

### Tabs

- One tab per visible chat, newest first, in t3code's panel tab look (spec 12; the old folder shape is gone): a 24 px kit ghost Button row, muted, the active one on the accent in the foreground colour. As many tabs show inline as fit the strip's width, newest first, and the rest sit behind a **More (N)** menu, N being how many are hidden. The fit is measured against a row of every tab at its natural width, kept out of sight, and recomputed when the rail resizes. The rule is the domain's `inlineTabs`: the newest chats that fit beside More, with the active chat always among them; at least the active tab shows, shrinking to fit. The active tab is never under More.
- **Label**: the chat's title (the person's or the agent's), else the first 32 characters of its first message plus an ellipsis when cut, else "Chat". The tooltip is the label, then " · " and the opening words, when they differ.
- **Rename**: double-click an inline tab to edit its name in place, in a compact kit field that grows with the text. Enter or blur commits, Escape abandons, an empty name clears it (`thread.meta.update {title: ""}`), so the tab falls back to its default and the agent may name it again. Renaming is allowed mid-turn. A row in the More menu does not rename on double-click; its menu's Rename (below) chooses that chat, which makes it an inline tab, and puts the field on that tab.
- **Tab menu**: a right-click on an inline tab chooses it and opens the kit Menu below it, and so does a click on the active tab (the second click of a double-click renames instead). A chat under More has the same menu: a right-click on its row chooses it, so it becomes an inline tab, and opens the menu below the More trigger. A click on a row under More chooses it and closes the More menu. The menu is at most 260 px wide; a long label is cut with an ellipsis and shown whole in a tooltip. A right-click anywhere else in the rail opens nothing: the canvas's context menu never opens over the rail, and a text field keeps the browser's own. The menu, named "<tab label> actions", has Rename, which starts the rename above; Detach (below), when the chat is linked to an artifact still on the canvas; and Delete, disabled while that chat runs, which opens the header's "Delete this chat?" confirmation for that chat.
- **Detach** unlinks one page or motion from the chat by dispatching spec 07's `thread.tags.remove`. Linked to one artifact on the canvas, the menu has one item, "Detach from <label>" (unlink icon); linked to several, a "Detach from" item opens a submenu listing them in tag order, each with its kind icon and label (its title, else its file name, as the recap card names it). Tags whose artifact is gone are not offered. It asks nothing: the chat stays, and only the link goes, so the tab leaves the filter for that artifact and the chat stops being continuable for it. When the agent in that chat later writes to or edits the artifact, the link comes back (spec 07's Tags). Detach works mid-turn and from the keyboard (ArrowRight on "Detach from" moves focus into the submenu). A toast (the app's info toast) says "Detached from <label>" with **Undo**, which dispatches spec 07's `thread.tags.add` for that artifact, so the link comes back at the end of the chat's tags.
- **Filter**: with no artifact selected, every chat shows. With one or more artifacts selected, only chats whose tags include any of them. A chat whose tagged artifacts are all deleted still shows.
- **Active tab**: the one last chosen if it is still visible; else the newest visible one; else none. With none, the next message starts a chat. The active tab is always inline.
- **Status**: each tab, and each row under More, ends in one icon. A spinner (the kit's Spinner) while the chat's turn runs, including while it waits on an approval. A checkmark (the kit's Check, in the success colour) when its turn finished since the person last viewed the chat. A warning (the kit's CircleAlert, in the destructive colour) when its turn failed since then. Nothing when it is idle or was viewed after its last turn. The active chat counts as viewed, so a turn that finishes in it shows nothing. The rail records each chat's state whenever it sees the chat (the active one every time), and a chat whose state has moved on since shows its checkmark or warning. The records live on the client for the session: closing the rail keeps them, and a reload starts from the chats' states as they are then.
- **Empty strip**: "No chats yet" with nothing selected; "Nothing said about these yet. Your first message starts a chat." with two or more artifacts selected; nothing with exactly one (the composer already asks for the first message).

### Thread search

Added from t3code. A search button in the rail header ("Search chats"), and Cmd+K (Ctrl+K elsewhere) while focus is in the rail, opens a field over the tab strip, placeholder "Search chats". From 2 characters (at most 200), after a 200 ms pause, it calls `orchestration.searchThreads {projectId, query, limit: 50}`. The engine matches, case-insensitively, the person's messages and each turn's final agent reply (never titles, reasoning or streaming text) in this project's chats that are not deleted, and returns one row per chat, `{threadId, source: "user" | "assistant", snippet, messageCreatedAt}`, the snippet at most 240 characters around the match, user matches first, then newest chat first. The limit is 1 to 50. The web also matches chat titles locally as a fallback. Each result shows the tab label, then "You:" or "Agent:" and the snippet with the match in bold. Choosing one makes it the active chat, even when the selection filter would hide it, until the selection next changes. Escape closes the search. No result: "No chats match."

### No provider ready

When neither provider is ready the transcript area shows the kit's empty state (spec 12), the provider lines in an alert frame:

- "No Claude or Codex found on this Mac." (on other platforms: "No Claude or Codex found on this computer.")
- "Install one and sign in, and the agent runs on your plan. Nothing is sent anywhere until then."
- One line per provider: its name in bold, then " · " and its status message, or " · checking…" while a check runs, or " · not checked yet". A `not_installed` provider adds a **How to install** link (its install page, new tab).
- A **Check again** button (refresh icon) that calls `providers.getStatuses {refresh: true}` and shows a busy state while it runs.

Send is disabled and the composer's placeholder reads "Connect Claude or Codex to start".

### The selection toolbar's Agent button

The selection toolbar (spec 03) ends with a filled **Agent** button (sparkles icon); its tooltip, when no provider is ready, is the provider message. Clicking it opens the composer (spec 03) in its Agent tray, anchored where the toolbar was, on the current selection:

- The selection enters as context chips (below).
- Under the chips, which chat this joins: "continues *<chat label>*" or "new chat", and a ghost button to switch: "New chat instead" or "Continue the earlier chat" (the latter only when a continuable chat exists).
- **Continuable chat**: the newest chat that is not running, is not an outside chat (spec 14: an outside agent reads no message from Unframed), and whose tags include **every** selected artifact. With no artifact selected, the newest non-running chat with no tags at all. This is all-of on purpose, unlike the strip's any-of: a chat that never saw B must not answer a message about A and B. The web computes this label itself from the chat list it already holds; the engine applies the same rule when the message arrives.
- While it is open, clicking another shape adds it to the message's context (idempotent, and the shape stays selected); clicking empty canvas closes the composer; Escape and Back ("Back to tools (Esc)") do the same.
- **Send** opens the rail on the target chat first, then sends, so the reply streams where the person is already looking. A new chat is created tagged with the selected artifacts.
- The composer's footer reads "<provider name> · not metered" beside Send.

### Recap card

After the last message of each turn that touched anything, a recap card on the card surface with the kit's border and radius:

- Header: a chevron, "<n> file" or "<n> files", and Hide/Show. Open by default.
- One row per artifact or project file the turn read or changed, in first-touch order: the shape kind's icon (an empty slot when there is none, so names line up), its label (title, else original file name without `.html`, else id), then **Editor** (opens the editor; spec 09 registers the editor, and until it does the row shows Locate only) and **Locate on canvas** (crosshair icon; pans and zooms to the shape; absent in embedded mode). A row whose shape is gone is struck through, greyed, and reads "deleted" instead of the buttons.
- Reads and writes are not distinguished. `canvas_read` contributes nothing (it reads everything, every turn), and neither does a call that failed or was refused, since it touched nothing. The rows come from the turn's `page_*`/`motion_*` tool inputs, the shapes its `canvas_write` ops named, and its turn changes; they are derived from the activities, not stored separately.
- Footer: **Revert this turn**, shown when the turn has turn changes and is not running. After a revert the button becomes the text "Reverted", and when shapes were skipped a line follows: "Left <n> shape(s) alone because they changed since: <label> (by the person), <label> (by another chat)." With every shape skipped: "Nothing to revert: everything this turn changed has changed since."
- **View diff** on a row for a page or motion the turn rewrote (see diffs below).
- **Spend line** (spec 14, any turn that started one): when the turn started paid generations, a line under the rows reads `Spent $<total> on <n> generation(s)`, with the total of the costs that have landed. A generation still running is counted in `<n>` and not yet in the total.

### The Agent tray

The composer is one component (spec 03) with two trays. This spec builds its Agent tray, 1:1 on t3code's composer (`apps/web/src/components/chat/` and its composer editor), on the kit and tokens of spec 12: t3code's composer shell (the rounded glass box with the composer shadow), its round message-action Send and Stop, kit Badge chips, Popover and Select pickers with t3code's picker rows, and the kit menu look for the `@`, `/` and `$` menus. It shares the Generate composer's 420 px. Where a detail below is not stated, follow t3code.

**Editor.** Tiptap with StarterKit minus blockquote, bullet and ordered lists, code block, heading, horizontal rule, link, underline, dropcursor, gapcursor, trailing node and code, and with bold, italic and strike off, so typed markdown markers stay literal. Custom atom nodes for context chips, mentions and skills; ArrowLeft and ArrowRight step over a whole chip in one press. The draft's plain text is the source of truth.

- Enter sends; Shift+Enter and Option+Enter insert a line break; Enter never sends during IME composition or while held down (t3code's: a repeated Enter breaks the line).
- **Send shortcut** (t3code's `sendShortcut`): the `agent.sendShortcut` preference in spec 01's preferences store, its control in spec 10's settings dialog. `enter` (the default) as above; `mod-enter-multiline` sends a one-line prompt with Enter but needs Cmd+Enter (Ctrl+Enter off Mac) once the prompt has a line break, Enter then breaking the line; `mod-enter` always needs Cmd+Enter. Cmd+Enter sends under every setting. The rule (`composerKeyIntent`, t3code's `composerSubmissionIntentForKey` with its default bindings) also places the follow-up chords below (Send and Stop, Queued messages) and Send and new chat. An open `@`, `/` or `$` menu takes Enter whichever Enter sends.
- **Send and new chat** (t3code's `composer.sendAndNewThread`, and its `composer.sendBackground` on Cmd+Option+Enter): in the rail, Cmd+Option+Enter (Ctrl+Alt+Enter off Mac) sends as Enter would (a running chat's message queues or steers by the Follow-up behavior), then shows the rail's new chat with the box still focused; from a new chat it starts that chat and comes back to a new one. It does not switch when it answers a question, updates a queued message or implements a plan. In the toolbar's tray it sends as Enter does.
- **Type and paste to focus** (t3code's `composerFocusRedirect`). With the focus in the rail but not in a field (after a click on the transcript, on empty rail, or on a chat tab: a click there focuses the rail itself), a printable key without Cmd, Ctrl or Option goes to the end of the box and focuses it, and a text paste goes there too (a large paste becomes a file as above; Cmd+Shift+V pressed first keeps it inline; a paste with files is left alone). t3code's guards: nothing is redirected from a field, a button, link, menu item, option, radio, switch or checkbox (the rail's chat tabs are the one exception, Space excepted, since they have no keys of their own), while any open dialog, menu, select, popover or sheet other than the one the rail sits in, or after another handler took the key. The listener is on the rail, so a key on the canvas, where tldraw owns the keys, is never redirected.
- Placeholder, in order of precedence: "Resolve this approval request to continue" (an approval is pending); "Choose an option above" (a choice-only question is pending) or "Type your own answer, or leave this blank to use the selected option"; "Add feedback to refine the plan, or leave this blank to implement it" (a plan follow-up); "Connect Claude or Codex to start" (no provider ready); otherwise "Ask, or say what should change… @ to mention, / for commands".

**Context chips: the selection enters as chips.** When the Agent tray opens, and whenever the canvas selection changes while the draft is empty, the chip row above the editor holds one chip per selected shape: an artifact as its kind icon and label; everything else collapsed into one count chip ("3 inputs", or "1 image" when all the same kind). Each chip has a remove button; removing a chip trims the message's context and leaves the canvas selection alone. Once the person has typed, a selection change adds new shapes as chips and never removes chips on its own. The chips are the message's `context.selection`; spec 07 builds the "Selected:" preamble line from them. The row is absent when there are no chips, since nothing selected means the whole canvas.

**Mentions.** Typing `@` opens a menu of the project's shapes (prompts, groups and every shape a person named by `@id`, other artifacts and media by label) and project files. Choosing one inserts an inline chip, serialised in the text sent to the model as `[<Kind>: <label>; ref=<id>]`, and adds the shape to `context.selection`. Arrow keys move, Enter or Tab choose, Escape closes. Empty state: "No matching shapes or files."

**Attachments.** Paperclip button "Attach files"; drag onto the rail shows the overlay "Drop files to attach" and highlights the composer; paste of files attaches them. Images show as a 64 x 64 thumbnail shelf ("Preview <name>", "Remove <name>", upload progress "NN%", "Retry upload for <name>" on failure); other files as chips with name and size ("upload failed" on failure). Files upload as they are staged (spec 07's upload flow), so Send only carries ids. Before upload the browser converts HEIC and HEIF to JPEG (extension becomes `.jpg`; a source over 50 MiB or 64 megapixels fails as too large) and downscales an image over 10 MiB ("'<name>' is too large to attach, even after compression." when it cannot). Limit breaches show spec 07's messages in the rail's error line.

**Attachments in the text** (t3code's attachment references). A file pasted or dropped while the draft holds text of the person's own (chips aside) also puts a chip in the text at the caret once it is uploaded, a space on either side as needed; into an empty draft it only attaches, and the Attach files button never adds a chip. The chip reads like a mention, `[Image: <name>; ref=<id>]` or `[File: <name>; ref=<id>]` with the name's `[`, `]` and `;` dropped, and the id is the uploaded attachment's, which names the file in the preamble's attachment line. Removing an attachment from the shelf removes its chips. Deleting a file's chip from the text removes the file, and undo brings both back; deleting an image's chip leaves the image. A chip of an attachment the draft does not hold, pasted or brought back by undo (one copied from another unsent draft of the project, say), adds that attachment to the draft: the bytes are already in the data folder under its id. A file whose draft was switched away from while it uploaded lands in that draft, its chip appended to that draft's text.

**Large paste.** A paste of 32 KiB or more (counted as characters or UTF-8 bytes), or one that would take the draft past 120,000 characters, becomes a text file attachment named `pasted-text.txt`, then `pasted-text-2.txt`, `pasted-text-3.txt`, typed `text/plain;charset=utf-8`. A toast says "Large paste attached as <name>" with "<size> · Use ⌘⇧V to keep a large paste inline." (Ctrl+Shift+V off Mac), and Cmd+Shift+V pastes inline. A pasted image always attaches; files pasted with text keep the text.

- Search strips the leading `/` and ranks exact, then prefix, then word-boundary (`-`, `_`, `/`), then substring, then fuzzy matches on the name, with description matches after; ties go built-ins, provider commands, skills. Arrow keys move, Enter or Tab choose (the first item when none is highlighted), Escape closes. Empty: "No matching command."; skills loading: "Searching skills..."; no skills: "No skills found. Try / to browse provider commands."

**Footer row**, on one line, left to right: attach, model picker, traits picker, the More composer controls menu, context window meter, then Stop and Send. Nothing overlaps at any width: the icon buttons, the meter and the Stop and Send group keep their size, and the traits label, then the model label, truncate first.

Cmd+Shift+E (Ctrl+Shift+E off Mac) with the box focused opens it (t3code's `composer.effort`). t3code's commands that raise or lower the effort by one step have no default keys there, so none are bound here.

**More composer controls** (t3code's compact controls menu, which it shows below 620 px of composer width; every composer here is narrower). A ghost icon button (ellipsis) labelled "More composer controls" opening the kit Menu above it: a "Mode" group with Build and Plan as radio items, only while plan mode is on, then an "Access" group with the four runtime modes as radio items, each with its icon, label and description. Usable while a turn runs (spec 07 applies the access mode to the next tool call). Shortcut Cmd+Shift+A while the composer has focus opens it. Escape in it closes the menu only.

**Plan mode is off unless set**, as t3code ships it. The `agent.planMode` preference (spec 10's Plan mode (legacy) switch) turns it on. **Context window meter.** A 20 px ring in a 28 px ghost button, filled to the share of the context used (from spec 07's token usage), in the highlight colour, turning to the error colour above 90%. Its label reads "Context window NN% used" (one decimal under 10%), or "Context window <N> tokens used" with no known maximum. Hovering for 150 ms opens a popover: "Context Window", "NN% · <used>/<max>" (tokens as `N`, `N.Nk`, `Nk`, `N.Nm`), a progress bar, "Total processed <N>", "Context compacts automatically when needed.", and a **Compact context** button that sends the provider's compaction (disabled with "Compaction is unavailable for this provider" when it has none).

**Send and Stop.** Send is disabled with no provider, with an empty draft and no attachments, or with a draft over the length limit. While a turn runs, Stop ("Stop generation") interrupts it, and Send says what the message will do (t3code's primary action): "Queue message" with a list-plus icon, or "Steer message" with a corner-up-right icon, by the Follow-up behavior setting, and the other while the other action's chord is held: Cmd (Ctrl off Mac), or Cmd+Shift when the Send shortcut needs Cmd for this prompt. Its tooltip reads "Click to queue, ⌘-click or ⌘Enter to steer" under Queue and "Click to steer, ⌘-click or ⌘Enter to queue" under Steer ("Ctrl-click or Ctrl+Enter" off Mac), with "⇧⌘Enter" ("Ctrl+Shift+Enter") in place of the chord when the Send shortcut needs Cmd for this prompt. A Cmd-click or Ctrl-click does the other action for that one message.

**Resume thread** (t3code's `useComposerResume`). When the chat's latest turn was stopped (`interrupted`) or failed on a usage limit (as t3code's resumable run), no turn runs, nothing is asked, no queued message is open and the box holds no text and no file, Send is replaced by "Resume thread": the same round action with a filled play icon and that tooltip. It sends "Continue where you left off." as a message of the person's own, so the provider, which kept the stopped turn's work in its session, carries on. Typing or attaching brings Send back. A turn cut off by an engine restart is not offered it: Claude resumes at the last turn that finished (spec 07's resume cursor), so the provider has nothing of the cut-off turn to continue, and the quit-mid-turn sentence's "Send again" stays the way back.

**Compact before send** (t3code's resume compaction chip). On a Claude chat whose context (spec 07's token usage, the latest `context-window.updated` activity) is 200k tokens or more and was last reported 70 minutes ago or longer (Claude's one-hour prompt cache plus slack; spec 07 reports no cache TTL), a chip sits left of Send: a minimise icon, "Compact" and the token count (`formatTokens`), on the kit's warning outline, `aria-pressed`, labelled "Compact <N> tokens of history before sending", tooltip "Next send compacts <N> tokens first." / "Click to keep full history". Send is then labelled "Compact and send", and sending dispatches `/compact` (the provider command the meter's Compact context sends) and puts the message in the chat's queue, so it goes once the compaction turn ends and shows in Up next meanwhile. Clicking the chip turns it to "Full" (the outline look, not pressed, tooltip "Next send keeps all <N> tokens." / "Click to compact first"), and the next send goes as it is; a send turns the chat back to Compact. The chip is offered only when the chat has a message other than `/compact`, the provider has `/compact`, no turn runs, nothing is queued, and no approval, question, plan to implement or queued edit is open; a message that is itself `/compact` never compacts twice. "Now" is read at each render and at least once a minute.

**Prompt length.** While the draft is over spec 07's 120,000-character limit, a red line under the editor says "Prompt is N characters over the 120,000-character limit. Shorten or split it before sending." (spec 07's sentence) and Send and Enter do nothing.

**Queued messages.** A message sent while a turn runs is queued in the browser (not the engine) under the person's **Follow-up behavior** setting, Queue (the default) or Steer, stored as the `agent.followUp` preference in spec 01's preferences store (so it survives the packaged app's new origin on every launch); its control is in spec 10's settings dialog, and until spec 10 lands it is always Queue. Cmd+Enter does the opposite of the setting for one message. When the Send shortcut needs Cmd for this prompt (t3code's resolution), Cmd+Enter does the setting and Cmd+Shift+Enter the opposite, and Cmd+Shift+Enter in the box then no longer steers the oldest queued message (its button on the row still does).

- Queue: the message waits and is dispatched after the running turn's next completed tool call or when the turn ends, one per boundary, in order.
- Steer: the message is dispatched at once with `steer: true` and joins the running turn.
- Queued messages show above the composer in t3code's **Up next** list (QueuedRunsControl), not in the transcript: a header with a list icon, "Up next · N queued", then one row per message in the order they go, each a right-aligned bubble with a dashed border and dimmed text. Under each bubble: its number, which turns into a drag grip on hover ("Reorder queued message N of M (drag, or press the arrow keys)"; dragging it drops the row above or below another, ArrowUp and ArrowDown on the focused grip move it one place; shown only with two or more rows), an Edit button (pencil, "Edit queued message", tooltip "Edit in the composer", with "(⌥Up)" or "(Alt+Up)" on the newest), **Steer** while a turn runs or **Send now** otherwise (corner-up-right icon; it steers the message in at once, tooltip "Send as a steer instead" or "Start a turn with this message", with "(⇧⌘Enter)" or "(Ctrl+Shift+Enter)" on the first row; Cmd+Shift+Enter sends the oldest), and an X, "Cancel and return to the composer", which gives the message back to the composer (Unframed keeps this rather than t3code's discard). With more than three, the first two show and t3code's "Show all N queued" / "Show fewer" control the rest. A bubble shows at most three lines (its full text in the tooltip). The rows scroll inside a list at most `min(28rem, 50vh)` tall, and when the rail is short Up next is the first thing above the composer to give up height: the list shrinks and scrolls, while its header, its Show all control, the approval, question and plan panels and the composer stay whole. Reordering is off while a message is being sent. Stop returns every queued message to the composer.
- **Editing a queued message** (t3code's queued edit). Edit on a row, or Alt+ArrowUp with the caret at the very start of the composer (the newest message), opens the message in the composer: its text, its context chips and its attachments. The chat's draft is set aside whole meanwhile (its text, chips, mentions and files), so nothing passes between the two; a draft handed back to the composer during the edit (a stash entry, a queued message given back) joins the draft set aside. The row reads "Editing in the composer" with a Cancel ("Cancel editing queued message"), and Send becomes a check icon, "Update queued message". While editing, chips can be removed or added from the canvas selection and files attached, pasted or dropped (with their reference chips in the text) or removed, as in a draft. Enter (or Cmd+Enter, by the Send shortcut) or Update replaces the queued message's text, chips and attachments in place, keeping its position, and the draft comes back with its files. Update waits for uploads in progress as Send does, and a failed upload blocks it with t3code's "Retry or remove failed uploads before saving." Cancel leaves the queued message as it was and puts the draft back. Cmd+S does nothing during an edit, since the box holds the queued message and not a draft. Editing is blocked while a question holds the composer, with the tooltip "Answer the question to edit queued messages", and a question that arrives mid-edit, or a switch to another chat, ends the edit as Cancel would. Stop mid-edit keeps the edit (text, chips and the files uploaded so far): it goes back to the composer with the other queued messages. If the message leaves the queue before it is updated (it was sent), t3code's rule decides: the edit counts as changed when its text, chips or files differ from the queued message's (chips and files compared as sets); an unchanged edit just closes; a changed one, all of it, stays in the composer as the chat's draft when that draft is empty, with the toast "Queued message is no longer queued" / "Your unsaved edit was kept in the composer.", and is dropped otherwise, with "Your unsaved edit was discarded."

**Prompt stash.** Cmd+S in the composer stashes the draft (text, chips and attachments) and clears it; up to 20 entries, the oldest dropped with the toast "Oldest stashed prompt discarded" / "The stash holds 20 prompts; the oldest was removed to make room." While the stash holds something, a "Stash" badge with the count ("Stashed prompts: N. Open stash.") sits above the composer's right edge, and its count pulses on each stash. The badge opens t3code's stash drawer, docked above the composer: a "Close stash" row with the count, then the entries, each a 90-character snippet (chips by their names; an entry with no text reads as what it holds, "(2 images)", "(1 file)", "(3 attachments)"), how many images and files it holds, a relative time and "Delete stashed prompt". While the drawer is open its keys come first, but only from the composer's box, the drawer or the badge (t3code's scoping): ArrowUp and ArrowDown move the highlight, Enter restores, Cmd+Backspace (Ctrl off Mac) deletes, Escape closes; a pointer down anywhere else closes it. Empty: "Nothing stashed yet. Press ⌘S with a prompt in the composer to stash it." With an empty composer Cmd+S restores the only entry, or opens or closes the drawer. A restored entry joins the draft (t3code's): its text after the draft's with a blank line between, its chips and attachments added, an attachment the draft already holds (same name, size and kind) not added twice. The stash is per project, stored as the `agent.stash.<project>` preference in spec 01's preferences store (text, chips and attachment ids; the attachments themselves stay in the data folder).

**Resting composer** (t3code's, `composerFooterLayout` and `composerScrollGesture`). In the rail, on a chat that exists, a wheel gesture over the transcript that moves it 24 px or more (in steps less than 120 ms apart, not toward the end once it is there, and not one a nested scroller inside the transcript takes), or PageUp or Home (not at the top) or PageDown or End (not at the end) with the focus in the transcript, rests the composer, provided the transcript is taller than its view. It does not rest, and a resting one opens again, while the prompt runs past one line (a line break, or text wider than the open box), while anything above or in the box asks for attention (an approval, a question, a plan to implement, an open `@`, `/` or `$` menu, the stash drawer, a drag of files, no provider ready, a notice, the length error, a queued message being edited, an upload in progress or failed), or in a window narrower than 640 px. Resting, the box keeps its chips and file chips, shows the prompt on one 32 px line (clipped, never wrapped) with up to three image thumbnails and "+N" for the rest, Stop and Send beside it, and the footer's controls in a strip under it in small muted type. A click anywhere in the box but its controls, a focus into it (not the window being refocused), typing (a wheel gesture still running when the person types does not fold it again), and scrolling down to the end of the transcript open it again; the strip's controls work without opening it. Switching chats opens it. The change is t3code's transition: the box's height moves over 240 ms on the drawer curve while the prompt line and Send slide from where they were, the arriving strip drifts in from 4 px above (the arriving footer from 4 px below, in the second half), and a transcript at its end stays at its end. Under reduced motion nothing moves or resizes over time: the arriving controls fade in over 160 ms.

**History.** ArrowUp in an empty composer recalls this chat's earlier messages, newest first, text only; ArrowDown past the newest clears. While a recalled message is unedited the arrows only recall from its first or last visual line (a long line wrapped in the box counts as several); editing it ends recall. After t3code's prompt history: a message repeated in a row is recalled once, mention chips are stripped from what is recalled, and implement-plan prompts and messages with no text of their own are skipped. History is off while attachments are staged or a question is shown. In-app chats hold only the person's messages, so there is nothing from automations or other agents to skip.

**Drafts** (t3code's composer drafts). The rail keeps one unsent draft per chat (and one for a new chat) on the project's chat client: its text, the context chips its @ mentions added, and its uploaded attachments. Context chips from the canvas selection stay with the composer, as before. Switching tabs shows that chat's draft with its attachments; the canvas rail and the editor's rail show the same draft for the same chat, so leaving the editor, closing the rail or switching chats loses nothing. Showing a chat's draft again is not an undo step: Cmd+Z after switching back does not empty it. Sending clears it. The toolbar's Agent tray keeps a draft of its own, kept the same way, since t3code loses nothing a person typed. Every draft is stored, 400 ms after its last change and when the page goes, as the `agent.drafts.<project>` preference in spec 01's preferences store (text, mention ids, and attachments by id; the files stay in the data folder), so a reload or a restart brings it back; local storage would not, since the packaged app's origin changes each launch. A deleted chat's draft is dropped at the next write. A file still uploading is not stored until it is done. An image restored by id (after a reload, from the stash, from Edit from here) shows its thumbnail from the engine's stored copy (spec 07's `GET /api/attachments/<id>`). Two windows on one project share the preference: the last write wins.

**Edit from here.** Under each of the person's messages, a ghost button with an undo icon, "Edit from here", disabled while a turn runs. It asks, in the kit's alert dialog: title "Edit from here?", body "Rewind chat to before this message. Your prompt and attachments return to the composer.", buttons "Cancel", "Revert canvas changes too" (destructive) and "Revert and keep changes". Either revert dispatches spec 07's `thread.checkpoint.revert` for the turns from that message on (with `restoreCanvas` true or false), then puts the message's text, chips and attachments back in the composer, after the draft as a restored stash entry is. A queued message given back (Cancel and return to the composer, Stop) joins the draft the same way. When canvas changes were skipped, the rail's error line says which, as the recap card does.

### The transcript

**Messages.** The person's messages are shown in t3code's message bubble (right-aligned, on the message surface), exactly as typed (never parsed as markdown), with their attachment chips and a "· N selected" note when they carried context; over 600 characters or 8 lines they collapse with "Show full message" / "Show less". Author headings: "You" and the provider's name.

**Markdown.** The agent's text goes through react-markdown with `remark-gfm` and `remark-breaks`, and t3code's prose typography (`ChatMarkdown` and its `.chat-markdown` rules, on t3code's tokens since spec 12). Raw HTML is never parsed: no `rehype-raw` and no sanitiser, so markup in a reply shows as the text it is. This is the one deliberate difference from t3code, for the same reason pages have their own origin. Links open in a new tab with `noopener noreferrer`; `javascript:` URLs are dropped. Code blocks get t3code's code block frame and toolbar ("Wrap lines" / "Disable line wrap", "Copy code" turning "Copied" for 1.2 s, a language badge). Tables scroll in a wrapper and offer "Copy as Markdown" and "Copy as CSV". No syntax highlighter is loaded.

**Streaming.** A reply renders through the same component while it streams, so formatting appears as it arrives. An empty final reply reads "(empty response)". Reasoning shows as a "Thinking" row while live, then "Thought", collapsed.

**Work log.** t3code's work log, derived from the chat's activities and drawn as t3code's timeline rows (an icon slot, the muted label, a chevron that turns as the row opens, and the opened detail on the muted fill):

- Tool calls of one turn merge by tool call id into rows with a label, a tone (thinking, tool, info, error) and a lifecycle state (in progress, completed, failed, declined, stopped). A row with a command, detail, changed files or image expands with a chevron.
- Consecutive rows fold into a group whose summary counts actions: "Read N files", "Changed N files", "Ran N commands", "Searched the web N times", "Searched code N times", "Used N tools", joined into one sentence ("Read 2 files, ran 3 commands, and changed 1 file").
- Live labels: "Running <program>", "Ran <program>", "Failed <program>", "Declined <program>"; an edit reads its path, or "<path> +N more".
- A context compaction (spec 07, from `/compact`, the meter's Compact context or Compact before send) reads "Compacting the context", then "Compacted the context", or "Couldn't compact the context" when it failed (spec 07: Codex refused the compaction, or a Claude `/compact` turn ended without compacting).
- Unframed's own tools (the artifact and preview tools arrive with spec 09; their labels are listed here so the work log has one table): `canvas_read` "Read the canvas", `canvas_write` "Changed the canvas (N changes)", `page_write` "Wrote page <title>", `page_read` "Read page <title>", `motion_write` "Wrote motion <title>", `motion_read` "Read motion <title>", `page_edit` "Edited page <title>", `motion_edit` "Edited motion <title>" (the title from the result when the call names only the shape), preview tools "Looked at <title> in a browser". Their groups count as "Changed the canvas N times" and "Used the browser N times". Spec 14's `generate`, in-app or outside, reads "Started an image generation", "Started a video generation" or "Started a text generation" when it is called, and an engine activity reads "Generated an image ($0.0420)", "Generated a video ($0.4100)" or "Generated text ($0.0012)" when its output lands, with the cost in the spec 03 form, or the label without the cost when none is known. Spec 14's `canvas_select` (outside chats only) reads "Selected <n> shapes" or "Cleared the selection", and it has no Revert. Spec 14's `file_add` (outside chats only) reads "Added <file name> to the project" ("Added a file to the project" when neither the result nor the path names it) or "Couldn't add a file to the project"; its `chat_note` makes no row, because the note shows as the agent's message.
- A call to one of Unframed's own tools that failed or was refused says what it tried: "Couldn't write page <title>", "Couldn't edit page <title>", "Couldn't read motion <title>", "Couldn't write component <title>", "Couldn't read the canvas", "Couldn't change the canvas", "Couldn't select <n> shapes", "Couldn't clear the selection", "Couldn't start an image generation" (or a video or text one), "Couldn't look at <title> in a browser", else "Couldn't run <tool>". A refusal returns no title, so `<title>` comes from the call's input, else the shape's title on the canvas, else its id. It counts in its group as the call would have. Any failed call opens to the error text the agent read: a refusal's `error`, else the result's text. A provider that hands over the result as text (Claude sends the MCP result's text parts) has it read as JSON where it is JSON. An outside chat's call ends with a `tool.failed` activity (spec 14), and its row is failed the same way.
- A settled turn folds behind "Worked for <duration>" ("You stopped after <duration>" when interrupted), durations as `1.2s`, `12s`, `1m 5s`.
- **Sub-agents** fold into one row per spawn: "Kicked off N subagents" with a status ("N working", "N failed", "✓ completed"); expanding lists each with its state and duration.
- Error rows stand alone and are never grouped.

**Activity line.** While a turn runs and no text is streaming, one line under the transcript says what the agent is doing: the label for the running tool ("Reading the canvas…", "Changing the canvas…", "Writing the page…", "Reading the page…", "Writing the motion…", "Reading the motion…", "Reading a file…", "Writing a file…", "Editing a file…", "Running a command…", "Looking for files…", "Searching…", "Fetching a page…", "Searching the web…", "Working on a sub-task…", "Planning…", "Looking for a tool…", else "Working…"), else "Thinking…". It is not cleared when a tool returns, because the gap after a tool is where the model thinks. From 10 seconds into the turn it appends the elapsed time as ` m:ss`. The clock is its own component so its tick never re-renders the transcript.

**Pending approval panel**, above the composer (t3code's, spec 12: a glass banner tinted in the warning colour, its heading in the warning colour): a header by request type ("Command approval", "File read approval", "File change approval", "App access approval", "App permission approval"), "1/N" when several are pending, the tool name, and its target in monospace with whitespace preserved (so padding is visible), at most 5rem tall and scrolling. The target is clipped at 300 characters for display; when clipped, a line reads "and <N> more characters not shown. Decline unless you know what they are." Under the target, the provider's reason (spec 07's `reason`) in small muted type, when it gave one. The answers are the ones the request offers (spec 07's `options`; t3code's `ComposerPendingApprovalActions`), else the fixed four: **Cancel**, **Decline**, **Always allow this session**, **Approve**. Decline (the kit's outline Button) and Approve (the default Button) are buttons; the others sit in a "More approval options" menu (an outline icon Button), which is left out when there are none. An answer with a warning shows a warning triangle before its label, the warning as its `aria-description` and in a tooltip on hover. They dispatch `accept`, `acceptForSession`, `decline`, `cancel`. The panel clears at once on a click; if the command is rejected it re-reads the chat and shows what is actually pending. The chat's tab shows its spinner while it waits.

**Pending question panel** (t3code's): a collapsible glass banner with the question's header, "i/N", and "Dismiss question without answering" (only for questions that do not block the turn); the question text, "Select one or more options." for multi-select, and t3code's option rows as kit ghost Buttons in the radio or checkbox role (the key, label and description, a check and the pressed fill on a chosen one; keys 1 to 9 when focus is outside a field; single-select advances after 200 ms). The question text is markdown, rendered as replies are (no raw HTML, links open in a new tab). A free answer is typed in the composer itself: while a question is shown the box holds its answer, and the draft typed before it is set aside, with its files, and comes back once the question is answered or goes. Files attached, dropped or pasted while a question is shown are that question's (t3code's per-question attachment draft): each question keeps its own as the person moves between them, a file alone answers a question that takes an answer of one's own, and they go with the answers as `attachmentsByQuestionId`. A question that takes only its options takes no file: Attach files is disabled and a drop or paste of files does nothing.

**Typing guard** (t3code's). An approval or question that arrives while the composer has focus and the person typed in the last 1.5 seconds is held back (not shown, the box not taken over) until they pause for 1.5 seconds, send, or leave the box. One already shown is never held again. The send button, t3code's message-action pill, reads "Next question", "Submit answer" or "Submit answers", "Submitting..." while it goes, with "Previous".

**Proposed plan card** (t3code's): a "Plan" badge and the plan's first heading as its title, else "Proposed plan"; over 900 characters or 20 lines it previews 10 lines with "Expand plan" / "Collapse plan"; a "Plan actions" menu with "Copy to clipboard" ("Copied!") and "Download as markdown" (`<slug>.md`). Above the composer a glass banner reads "Plan ready" and the title, with **Implement** (t3code's split message-action pill) (and a menu "Implementation actions" with **Implement in a new chat**) when the draft is empty, or **Refine** when the person has typed. Implement switches the chat to default mode and sends the text in `assets/prompts/implement-plan.md` followed by the plan; a new chat for it is titled "Implement <title>" (or "Implement plan"). Refine sends the draft as feedback in plan mode.

**Notices above the composer** (t3code's ComposerBannerStack). The rail's error line is a stack of glass notices directly above the composer, each fading in as it comes: the session's failure first (the connection and the agent), then what failed here (a refused command, a limit breach). A notice reads as one line with its icon; when that line is clipped, an info button ("Show full title: <text>") opens a popover with all of it on hover or click. Each has "Dismiss error": a failure from here is cleared, the session's is hidden for that chat and text while the app runs. The toolbar's Agent tray shows the rail's failures the same way above its composer. A notice may carry a second, muted line under its title. **Usage limit reached** (t3code's `UsageLimitRecoveryBanner`): when the chat's latest turn failed on a usage limit (its latest rate-limit notice says `rejected`), a warning notice with a gauge icon reads "Usage limit reached", and under it "Resets <when>" (the transcript's reset moment) or "Reset time unavailable; retry manually"; it goes once a turn goes through, and the composer offers Resume thread meanwhile. t3code's "Resume at reset" and "Snooze until reset" are left out: t3code runs them on its server (a recovery worker that starts the turn when the limit resets, and thread snooze), and spec 07 has no scheduler and no snooze. Up next and the approval, question and plan panels stay as they are, as t3code keeps them out of the stack. While the rail is docked open, the app's bottom-left toasts start past its right edge, so a toast never covers the composer.

**Failure, retry and limit lines.** A failed turn's reply already ends with its failure sentence (spec 07). The rail's error line shows only failures the transcript cannot (a session that never started, a lost connection), and is hidden when it repeats the last message. A retry reads "The API is busy (529), retrying in 2s. Attempt 1 of 3…" (status and wait omitted when unknown). A usage limit that was hit reads "You have hit a usage limit. It resets <when>." (or "You have hit a usage limit."), from the activity's `resetsAt` (an ISO 8601 time, spec 07) in local time. The clock time is hour and minute on a 12-hour clock with am or pm ("8:00 am", "3:30 pm"), whatever the locale. `<when>` is "at <time>" when the reset is today, "<weekday> at <time>" one to six days away ("Friday at 8:05 am"), and "on <day> <month> at <time>" otherwise ("on 16 October at 8:05 am"), so a weekly reset never reads as today. It clears when the next turn starts. A "close to the limit" warning shows nothing: Claude sends it on every turn once a plan's window is nearly used.

**Empty chat.** A chat with nothing in it shows one line at the foot of the transcript, as plain text: "Ask about what is on the canvas, or say what should change or be made. Whatever is selected comes with the message as context."

**Scrolling.** Sending anchors the new message near the top; the view follows live output while within 40 px of the end; otherwise a "Scroll to end" pill appears (t3code's: the kit's glass Button).

### Checkpoint diffs for page and motion files

t3code shows a turn's changes as a diff computed from checkpoints. Unframed's checkpoints are free: every page or motion write is a new file, and spec 07's turn changes record the file a shape named before and after each turn. So:

- `orchestration.getTurnDiff {projectId, threadId, fromTurnCount, toTurnCount, ignoreWhitespace?} -> {files: [{shapeId, label, kind, before: file | null, after: file | null, additions, deletions, patch, tooLarge?}]}`: one entry per page, motion or component sheet written in turns `fromTurnCount + 1` to `toTurnCount`, `patch` a unified diff (3 lines of context) between the file the shape named before the first of those turns and after the last. A new artifact diffs against empty. One turn `n` is `{fromTurnCount: n - 1, toTurnCount: n}`.
- `orchestration.getFullThreadDiff {projectId, threadId, toTurnCount, ignoreWhitespace?}`: the same from the chat's start.
- `ignoreWhitespace` (the panel's "Hide whitespace changes") compares lines with every space taken out, as git's `-w` does.
- A file over 2 MiB answers "This file is too large to diff." in place of its patch, with `tooLarge: true` and no counts.

The diff panel is t3code's (spec 12: its diff panel shell on the background with the kit's border, a header row of kit controls, the segmented Stacked/Split toggle, t3code's diff colours for the counts and its injected diff CSS for the renderer): a scope menu ("Latest turn", "Turn N", "All turns"), a changed-files list down the side (one entry per artifact by label, with added and removed line counts), and the patch rendered with `@pierre/diffs` in a worker, with a Stacked/Split toggle (remembered as the `agent.diffLayout` preference), "Enable line wrapping" / "Disable line wrapping", "Show whitespace changes" / "Hide whitespace changes", and HTML highlighting. Empty states: "No completed turns yet." and "No page, motion or component changed in this selection." It opens from a recap row's **View diff** and from **View all changes** on the newest recap card, and closes on Escape or its close button. It opens beside the rail, on its left, as tall as the rail, and its renderer loads the first time it opens. Diffs are read-only: taking a change back is Revert, never a hunk-level edit.

## Testing Decisions

A good test does what a person does in the rail, the composer and the toolbar, and asserts on what is on screen and on what the engine then holds (the chat's projection, the canvas). It never inspects component state or the web's stores.

- **Browser seam** for nearly everything here: Playwright against the built web client served by an engine at the engine seam, with `UNFRAMED_TEST_AGENT_SCRIPT` pointing at the fixture folder, so every reply, tool call, approval, question, plan, failure and retry is deterministic. Provider readiness in the browser comes from fake `claude` and `codex` executables (spec 07), or from the scripted agent reporting itself ready. Motion is checked by asserting computed styles and transition end, with reduced motion emulated through Playwright. Timers (the elapsed clock, queue timing) use Playwright's clock.
- **Domain seam** for the pure rules: tab visibility (any-of), which tabs fit inline at a width, the active tab, tab labels, the continuable chat (all-of), recap rows, the work log derivation and its labels, the large-paste rule and file naming, slash command ranking, the context meter's formatting, how a restored draft joins the current one, prompt history, the follow-up action, the send shortcut and what each Enter chord does, the typing guard, moving a queued message and where a dropped row lands, whether a queued edit changed (text, chips and files) and what happens to one whose message leaves the queue, attachment chips (their text, finding, appending and removing them), which drafts are stored and how they are read back, a stash entry's snippet, the notices' order, when the composer rests (the conditions, the scroll gesture, the scroll keys, when the transition runs, the resting thumbnails), and when compacting before a send is offered and whether a send compacts.
- **Engine seam** for the two engine additions: thread search and artifact diffs.

Prior art: t3code's own web tests for the composer logic, the work log and the timeline (pure functions over activities), and the old app's rail rules tests (visible chats, active tab, tab label, continuable chat, recap rows).

The embedded rail is exercised by spec 09's editor tests, since the editor is what mounts it.

## Further Notes

- **Kept from the old app, unchanged:** the rail's size and motion; the header actions; tabs that fit inline with the rest under More (N); double-click rename; the any-of filter and the all-of continue rule (they answer different questions and must not be merged); the no-provider state; the activity line and its labels; the recap card with Editor (named Open in the old app), Locate and struck-through deleted rows; markdown with no raw HTML; the toolbar's continues/new chat line.

Your first message starts a chat.", "The API is busy (529), retrying in 2s. Attempt 1 of 3…", the plan toggle tooltips).
- **The old targeting words.** The design board for the toolbar says one artifact selected is the target, none means a new artifact, several means it asks. That is now how the agent is told to read the selection (spec 07's system prompt), not a field in the message: there is no target and no mode picker, and "asks" means the agent asks in its reply only when the sentence is genuinely ambiguous.
