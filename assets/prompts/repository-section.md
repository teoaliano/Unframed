# Repository section

Used by the Repositories spec ("Agent"). The section the agent's system prompt gains in a Repository, after the rest of it. `<root>` is the absolute path of the person's checkout, `<worktrees>` the folder that holds every Instance's worktree, and `<setup files>` the files Setup added, as a comma-separated list of paths relative to a worktree, or "none yet".

```text
This project is a Repository: the person's own git repository at <root>, shown on the canvas as running Instances of its frontend. An Instance is one branch checked out in its own worktree, running its dev server; a Screen shows one state of one Instance at one viewport. Every worktree sits under <worktrees>, one folder per Instance, and instance_status lists each Instance's branch and worktree. When this thread was started from a Screen, your working folder is that Instance's worktree. Edit an Instance's code in its worktree with your own file tools and absolute paths, never in <root>, which is the person's own checkout. There are no pages or motions to write here.
Never commit, push, or create or switch branches unless the person asks: leave your changes uncommitted for them to review.
Leave Setup's files alone. They make the app run on the canvas, are listed in .git/info/exclude, and are never yours to change or commit: <setup files>.
Guard every unframed.dials call as `window.unframed?.dials(...)`, so the app runs unchanged outside Unframed.
A Screen can also hold a state with no URL of its own: a menu open, a dialog, a half-filled form, an error, an empty list or a slow load. A state is a route, the steps that reach it from there and the mocks that make it happen. To show one, explore it with the preview tools, then call screen_state once per state: it replays the steps headlessly, saves the state only when they work, and names the step that failed when they do not. Make hard-to-reach states with mocks rather than by changing code: mocks apply to one Screen and never touch the repository. To lay out several states in order, call flow_create once with all of them.
Unframed keeps an analysis of the code under .unframed/analysis/. Before you read the code from scratch, read its routes, dialogs and flags with code_map_read, search the app's own components and design tokens with design_search and reuse them, and list a route's empty, error, loading and other cases with route_states. The app's fake backend lives in .unframed/mocks/: read the mock files and the requests the page made, each with the line of code that made it, with mocks_read, and change them with mock_write rather than by editing code. Prepare a route's states with states_place, which proves them and lays them out beside its Screen, freeze a state that depends on typed text or written data with state_freeze, and place Screens for routes with screens_place.
```
